# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Classlog (학급 대시보드) — a Korean-language classroom management dashboard. A teacher logs in and gets five sections behind a shared sidebar (`AppShell`): 홈 (home — NEIS weekly timetable/meal/schedule cards), 정보관리 (student roster CRUD, CSV bulk import/export, school/NEIS settings), 학급기록 (roster browsing + per-student life/counseling records), 출결관리 (monthly attendance grid + summary), 자리배치 (seating-chart generation with constraints). `README.md` is stale (still describes only the original roster/records MVP) — treat this file and `docs/superpowers/specs/` as the source of truth for current scope.

Deployed at https://classlog-ten.vercel.app, auto-deployed by Vercel on every push to `main` (see Deployment below).

## Commands

```bash
npm run dev              # start the Vite dev server
npm run build             # tsc -b (typecheck) && vite build
npm run lint               # oxlint
npm test                    # vitest run (all tests)
npm test -- <pattern>       # run only test files matching <pattern>, e.g. `npm test -- csv`
npm run preview             # preview the production build
```

There is no `test:watch` script; use `npx vitest` directly for watch mode.

**`npm run build`'s `tsc -b` does not type-check `api/`** — `tsconfig.app.json` only includes `src`, and `tsconfig.node.json` only includes `vite.config.ts`. A broken `api/neis.ts` (wrong import path, wrong Node types) will pass `npm run build` and `npm run lint` locally and only fail once it hits Vercel's build step. This has already happened once in practice (two consecutive "repair NEIS serverless function" fixes were needed after a change that looked fine locally broke production). When touching anything under `api/`, verify it against Vercel's deployment status/logs, not just the local build.

### Supabase setup (required before the app can run)

1. Run `supabase/schema.sql` in the target Supabase project's SQL editor. It creates five tables: `students`, `records`, `attendance`, `seating_plans`, `school_settings`. `create table if not exists` is idempotent only against a project with none of these tables yet — against a project that already has them with a different column set (e.g. after a student-field schema change), this is a no-op that silently leaves the old columns in place. To apply a schema change to an existing project, drop the affected tables first (`drop table if exists records; drop table if exists students;` — this deletes all data) and re-run the file. Re-running `create policy` statements will also error if the policies already exist; drop them first on a re-apply. Note that `schema.sql` also contains a couple of standalone `alter table ... add column if not exists` migration statements below the initial `seating_plans` create (for columns added after that table already existed elsewhere) — these are safe to re-run and don't need the drop-and-recreate dance.
2. Create a teacher user under Authentication → Users in the Supabase dashboard (no self-service signup UI exists).
3. Copy `.env.example` to `.env` and fill `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` from the project's API settings.

### NEIS integration setup (required for 홈/정보관리's school-lookup features)

Get a free API key at https://open.neis.go.kr and set `NEIS_API_KEY` in `.env` (server-only — deliberately **not** `VITE_`-prefixed, since that would bundle it into the client JS). `npm run dev` reaches NEIS through a Vite dev-server middleware (`neisDevProxy` in `vite.config.ts`) that mirrors the production serverless function; no separate `vercel dev` process is needed locally. In production the same request goes through `api/neis.ts` on Vercel. A teacher must also fill in 학교/학년/반 under 정보관리's school-settings section (`school_settings` table, `useSchoolSettings`) before the home cards or attendance calendar's school-event overlay have anything to query — without it those sections render an empty/idle state, not an error.

## Deployment

The GitHub repo is connected to a Vercel project (`classlog`) that auto-builds and deploys every push to `main` — no manual deploy step. `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` (build-time) and `NEIS_API_KEY` (server-only, read at request time by `api/neis.ts`) all must be set **separately** in the Vercel project's Settings → Environment Variables (`.env` is gitignored and never reaches Vercel). Missing `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` has already caused a real outage once: the production build silently baked in `undefined` for both, `createClient` failed during module init before React ever rendered, and the site was a blank white page with no console error visible to the extension-based debugging tools. If you change a required env var, add/update it in Vercel too and trigger a redeploy (env var changes don't retroactively apply to an already-built deployment).

## Architecture

**Stack:** React 19 + TypeScript, Vite, React Router 7, Supabase (`@supabase/supabase-js` v2), Tailwind CSS v4 (via `@tailwindcss/vite`, no `tailwind.config`/PostCSS file — configured entirely through the Vite plugin and a single `@import "tailwindcss";` in `src/index.css`), lucide-react for icons. Tests run on Vitest + jsdom + Testing Library.

**Data access is hook-only.** `supabase` (from `src/lib/supabaseClient.ts`) is imported only inside `src/lib/hooks/*.ts`. Components and route files never call Supabase directly — they consume the hooks below. The one parallel exception is NEIS data: `src/lib/services/neis-service.ts` is a pure `fetch`-based module (no Supabase import) that the NEIS-related hooks call instead of `supabase.from(...)`; it talks to `/api/neis`, never to NEIS directly from the browser. Preserve both boundaries when adding features.

**Routing (`src/App.tsx`):** `/login` is public. Everything else nests under `<ProtectedRoute>` → `<AppShell>` (the sidebar layout, `<Outlet />`) so `ProtectedRoute`'s `useAuth()` call and the sidebar stay mounted across navigation (an earlier per-route-wrapper version caused a loading flash on every navigation, not just after login — don't reintroduce per-route wrappers). Protected pages: `/home`, `/students` (roster + records browsing), `/students/:id` (student detail), `/students/manage` (roster CRUD/CSV/school settings), `/attendance`, `/seating`. Any unmatched path redirects to `/home`. `AppShell` derives which nav item is "active" itself for `/students` vs `/students/manage` (`rosterActive` in `AppShell.tsx`) since both share the `/students*` prefix but are different sidebar entries (학급기록 vs 정보관리).

**Hooks (`src/lib/hooks/`):**
- `useAuth` — wraps `supabase.auth` (session state via `getSession()`/`onAuthStateChange`, `signIn`, `signOut`). Unlike the Supabase-table hooks it doesn't expose an `error` field; callers handle their own error state (see `LoginPage`).
- `useStudents` — fetches/creates/updates/deletes rows in `students`, plus `addStudents(rows)` (one bulk `insert([...])` request for N rows, not a loop) and `deleteAllStudents()` (one bulk `delete()` wiping the whole roster — RLS scopes it to the current teacher). All mutators return `{data|inserted, error}` and also set the hook's shared `error` state, then merge+re-sort local state by `number`. Consumed by both `/students` (read-heavy) and `/students/manage` (full CRUD) — one hook, two different UIs over the same data.
- `useStudentRecords(studentId)` — same CRUD shape, scoped to one student's `records`, sorted newest-`record_date`-first (ties broken by `created_at`).
- `useAttendance(yearMonth)` — CRUD over one month of `attendance` rows (`'YYYY-MM'` in, converted to a `[start, end)` date range internally via `monthRange`); enforces the DB's `unique (student_id, date)` constraint (one entry per student per day).
- `useAttendanceSummary(studentId)` — aggregate counts of `AttendanceStatus` for one student, used by the detail-page drilldown.
- `useSeatingPlans(yearMonth)` — CRUD over `seating_plans`; `yearMonth` accepts `'YYYY-MM'` to scope to one month or the literal `'all'` to fetch every saved plan (used to compute "avoid past neighbors/seats" history across time).
- `useSchoolSettings` — single-row (`maybeSingle()`) CRUD over `school_settings`, the per-teacher 학교/학년/반/NEIS 코드 record everything else in this section depends on.
- `useSchoolEvents`, `useWeeklyMeal`, `useWeeklyTimetable` — not Supabase hooks; they call into `neis-service.ts` given a `SchoolSettings` and a date range, exposing a shared `WeeklyFetchStatus` (`'idle' | 'loading' | 'success' | 'error'`) pattern instead of the table hooks' `{data, loading, error}` shape.

**NEIS integration (`api/neis.ts`, `api/_lib/neisProxy.ts`, `src/lib/services/neis-service.ts`):** `api/_lib/neisProxy.ts` holds the shared allowlist (`schoolInfo`, `elsTimetable`, `mealServiceDietInfo`, `SchoolSchedule`) and fetch-to-NEIS logic, imported by both `api/neis.ts` (the Vercel serverless function, production) and the `neisDevProxy` Vite plugin in `vite.config.ts` (`npm run dev`) — this is why the two entry points can't drift apart, and why a NEIS endpoint change only needs to happen in one place. `src/lib/services/neis-service.ts` (browser-side, ported from a sibling project, `KWON911/school_manage`) is the only thing that calls `/api/neis`; it never touches `NEIS_API_KEY` or the NEIS host directly. Because relative imports inside `api/` run as compiled Node ESM on Vercel (not bundled the way `vite.config.ts`'s import of the same file is), `api/neis.ts`'s import of `neisProxy` needs an explicit `.js` extension while `vite.config.ts`'s import of the same file needs `.ts` — they are not interchangeable; copying one import style into the other file's import breaks it.

**Roster split — 학급기록 vs 정보관리:** these are two different pages over the same `useStudents()` data, not one page with a mode toggle. `/students` (`StudentListPage`/`StudentListItem`, a dense grid of cards) and `/students/:id` (`StudentDetailPage`) are the read/records-focused pair — `StudentDetailPage` only shows 번호/이름, an attendance-summary badge row, and the 생활기록/상담 (life-record) timeline; it has no student-info view, edit, or delete affordance of its own. `/students/manage` (`StudentManagePage`, composed from `components/manage/StudentListCard` + `SchoolSettingsSection`) is the single home for all student-info admin actions: view (`StudentDetailModal`, a read-only `<dl>` opened from `StudentRowMenu`'s "상세정보 보기"), edit (`StudentForm`), delete one or all, CSV bulk import/export, gender breakdown, and the NEIS school-settings form. When adding a field to `Student`, three surfaces (`StudentForm`, `StudentDetailModal`, `src/lib/csv.ts`'s 12-column format) need updating independently — none is derived from the others.

**CSV import (`src/lib/csv.ts`):** a dependency-free, pure module (no React/Supabase imports) — hand-written parser rather than a library. The student-roster format is a fixed 12-column CSV (번호,성명,성별,생년월일,학생전번,주소,부성명,부전번,모성명,모전번,비상연락처,비고); `address` routinely contains commas (e.g. Korean street addresses), which is why the hand-written parser's quoted-field handling exists — a naive `split(',')` would break on it. `decodeCsvBytes` tries strict UTF-8 first and falls back to EUC-KR/CP949 (common for Excel exports on Korean locales) if the bytes aren't valid UTF-8. `parseStudentsCsv` detects an optional header row, validates each row (including a `raw.length < 12` shape check to reject legacy/malformed files instead of silently shifting columns), and reports both `valid` rows and `skipped` rows (each with a Korean-language reason) — nothing is ever silently dropped without a reason. `buildStudentsCsv` is the export direction, used by `StudentListCard`'s CSV-export button. `ImportStudentsPanel` is the import-side consumer, driving a preview-before-commit UI; it also links a downloadable template at `public/sample-students.csv` (must keep its UTF-8 BOM — see the encoding note above — or Excel on Korean Windows renders it as garbled text even though the app itself parses it fine either way). The repo-root `sample-students.csv` is a scratch copy for local testing, not referenced by the app.

**Seating (`src/lib/seating.ts`, `SeatingPage`, `useSeatingPlans`):** a dependency-free, pure module holding the placement algorithm — `createSeats`, `shuffle`, `areAdjacent`/`canUseSeat` (orthogonal/diagonal separation + gender-seat constraints), `placeStudents`/`generatePlacement` (the randomized-with-retries placer, scored by `scorePlacement`), and `derivePastNeighborPairs`/`derivePastSeatsByStudent` (mine prior `SeatingPlan`s, scoped by `filterPlansByScope`'s `PreviousSeatHistoryScope`, to avoid repeating recent neighbors/seats). Kept separate from `useSeatingPlans` (persistence) so the placement logic itself stays unit-testable without a Supabase mock.

**Data model (`supabase/schema.sql`, mirrored in `src/lib/types.ts`):** five tables, all `teacher_id`-scoped with RLS.
- `students` / `records` — `records` FK's to `students` `on delete cascade`. `students` columns: `number`, `name` (both required), plus 10 optional (`string | null`) fields — `gender`, `birthdate` (free text, source format like `240304`, not a date type), `student_phone`, `address`, `father_name`, `father_phone`, `mother_name`, `mother_phone`, `emergency_contact`, `note`. Father/mother are flat columns, not a normalized guardians table — the source template is always exactly one of each, so a join table would be pure overhead. `records.category` is a closed set enforced identically in two places: the Postgres `check` constraint and the `RecordCategory` TypeScript union (`생활지도 | 학습 | 진로 | 학부모상담 | 기타`) — keep both in sync if this set ever changes.
- `attendance` — FK's to `students` `on delete cascade`, `unique (student_id, date)` (one entry per student per day), `status` (`결석 | 지각 | 조퇴 | 결과`) and `reason_category` (`질병 | 미인정 | 인정 | 기타`) each closed sets enforced via `check` + a matching TS union, same pattern as `records.category`.
- `seating_plans` — `seats`/`assignments`/`separations` are stored as `jsonb` rather than normalized rows; a plan is read/written as one JSON blob per save, not reconstructed from child rows. Also carries `gender_balance`/`avoid_past_neighbors`/`avoid_previous_seats` booleans and `previous_seat_history_scope` (`check`-constrained to `PreviousSeatHistoryScope`) that parameterize `src/lib/seating.ts`'s placement.
- `school_settings` — one row per teacher (`teacher_id` is the primary key, not a separate `id` column — this is a 1:1 settings record, not a list). Holds the NEIS office/school codes plus 학년/반 used by the home cards, attendance calendar's school-event overlay, and NEIS lookups generally.

All RLS policies check `teacher_id = auth.uid()`; `records` and `attendance` additionally verify the referenced `student_id` actually belongs to the same teacher via an `exists` subquery, so a bulk-insert path can't smuggle a row onto another teacher's student. `seating_plans` does **not** have an equivalent check — the student ids inside its `seats`/`assignments`/`separations` jsonb aren't validated against `students` by RLS at all (a real FK/`exists` check can't reach into a jsonb blob the way it can a column), so that invariant is enforced only by the app, not the database.

**No app-level strict TypeScript.** None of the `tsconfig*.json` files set `"strict"`, so `strictNullChecks` is off — code that passes a `string | null` where a plain `string` is expected (or similar) will compile without complaint. This has bitten real code before (a `StudentForm`/`StudentDetailPage` mismatch caught only at `npm run build` during review); don't assume the compiler will catch nullability mistakes. Remember also that `api/` isn't covered by `tsc -b` at all (see Commands above) — nullability mistakes there won't even get the `npm run build`-time catch that `src/` gets.

## Testing conventions

Automated tests exist only for pure logic and hooks: `src/lib/csv.ts`, `src/lib/seating.ts`, `src/lib/services/neis-service.ts`, `src/lib/utils/{date-utils,schoolEvents,subjectDisplay}.ts`, and the hooks `useStudents`, `useStudentRecords`, `useAttendance`, `useAttendanceSummary`, `useSeatingPlans`, `useSchoolSettings`. There are no component or route tests (`src/components/`, `src/routes/`); those are verified by `npm run build` + `npm run lint` + manual smoke testing. Follow this split for new code rather than adding component tests.

Hook tests mock the Supabase client via `vi.mock('../supabaseClient', ...)` and the shared `createQueryBuilder` helper in `src/test/supabaseMock.ts`, which fakes the chainable query builder (`select`/`order`/`eq`/`insert`/`update`/`delete` all return the same builder; `.single()` and awaiting the builder directly both resolve to the configured `{data, error}`). **Any variable referenced inside a `vi.mock(...)` factory must be named starting with `mock` (e.g. `mockFrom`, `mockGetUser`)** — Vitest's mock-hoisting only exempts identifiers with that prefix; anything else throws `Cannot access before initialization` at runtime despite type-checking fine.

When writing a test that asserts ordering/sorting behavior, make sure the fixture data would produce a *different* result under the naive (unsorted) implementation than under the correct one — a fixture that's already in sorted order will pass even if the sort logic is broken or missing. This exact bug has occurred twice in this codebase's history and was caught only in review.

## Project docs

`docs/superpowers/specs/` holds one design doc per feature slice (written before implementation, describing scope and architecture decisions); `docs/superpowers/plans/` holds the corresponding step-by-step implementation plan. Not every shipped feature has a spec/plan pair — the NEIS home cards, sidebar/login redesign, and roster-page split landed without one — so absence of a doc doesn't mean absence of intent; check `git log` for the feature's commits if there's no matching doc. Check existing docs before making significant changes to understand why something is scoped the way it is — some items remain deliberate deferrals, not oversights: announcements, grades, multi-year class switching, student/parent-facing views, and guardian normalization into a separate table. (Attendance and seating charts were on that deferred list originally but have since shipped — don't assume this list is exhaustive or permanent; verify against current routes/specs before citing something as "out of scope.")
